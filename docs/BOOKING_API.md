# Booking API — Phase 1 contract

This document describes the implemented Go API and the interfaces available to the future booking frontend. The clinic owner has confirmed **automatic confirmation as the default**; manual confirmation remains an authenticated administrator setting. No booking frontend, account-creation checkbox, admin dashboard, email sender or reminder scheduler is included in this backend-only phase. The general-question form at `/kontakti` remains separate. The dedicated booking experience is planned for `/pieraksts`; no existing CTA destinations or public designs are changed here.

The working branch initially contained the API scaffold rather than the approved frontend/Auth source. The existing backend authentication implementation was recovered from `feature/homepage` at `f50e2aa`; frontend files and authentication flows were not replaced. See [BOOKING_PHASE_1.md](BOOKING_PHASE_1.md) for the database baseline, migration procedure and verification results.

## Common rules

- Base path: `/api`. Booking routes return `Cache-Control: no-store`.
- JSON request bodies require `Content-Type: application/json`, are limited to 16 KiB, reject unknown fields and must contain exactly one JSON value.
- IDs are UUIDs. Create requests additionally require a newly generated random UUIDv4 `Idempotency-Key` header.
- Appointment times are absolute RFC3339 instants. Responses generated by availability use UTC (`Z`). Always send the selected slot's exact `starts_at`; do not reconstruct it from a wall-clock label.
- Clinic dates, weekdays, advance notice and working hours use `Europe/Riga`. Render returned instants using this named timezone rather than the browser's default timezone or a fixed `+02:00` offset.
- A booking reference is a receipt identifier, not an authorization credential. There is no public `/appointments/reference/:reference` endpoint, guest detail lookup or public cancellation endpoint.

All examples below use synthetic identifiers and contact data. Example timestamps are illustrative, not advertised appointments. The frontend must select actual IDs and instants returned by the API.

## Public catalog and availability

### `GET /api/booking/services`

Returns services that are active, booking-enabled and have a configured duration, ordered by `sort_order` then ID. Names, optional descriptions and optional verified price-display strings are provided separately for LV/RU/EN. The frontend selects the appropriate localized field; this API does not accept frontend prices or durations when creating a booking.

```json
{
  "services": [
    {
      "id": "11111111-1111-4111-8111-111111111111",
      "slug": "development-procedure",
      "name_lv": "Izstrādes testa procedūra",
      "name_ru": "Тестовая процедура для разработки",
      "name_en": "Development test procedure",
      "duration_minutes": 30,
      "provenance": "development_fixture"
    }
  ],
  "privacy_notice_version": "development-fixture-v1"
}
```

The example duration is a fixture, not a clinic-confirmed treatment duration. Production migrations create no doctors, services or schedules. An unconfigured catalog returns `services: []`; `privacy_notice_version` may be `null`. The version is the bootstrap value for the required acknowledgement on submission. It identifies the clinic-approved notice presented by the future UI; it is not the legal document itself. Do not fabricate a version or show the booking flow as ready when catalog, schedules or the approved notice are missing.

### `GET /api/booking/doctors?service_id=<uuid>`

Returns `{"doctors": [...]}` containing each eligible doctor's `id`, `name` and `provenance`, ordered by `sort_order` then ID. The service must be bookable, the doctor must be active and booking-enabled, and their relationship must exist in `doctor_services`. A bookable service with no eligible doctors returns an empty array. An invalid UUID returns 400; a nonexistent or unavailable service returns 404.

### `GET /api/booking/availability?service_id=<uuid>&date=YYYY-MM-DD`

Optionally add `&doctor_id=<uuid>` for a particular doctor. **Omit `doctor_id` for any available doctor.** An empty value is also interpreted as omitted; the literal string `any` is invalid. The date is a Riga calendar date, not a UTC date.

```json
{
  "slots": [
    {
      "doctor_id": "22222222-2222-4222-8222-222222222222",
      "starts_at": "2026-10-20T07:00:00Z",
      "ends_at": "2026-10-20T07:30:00Z"
    }
  ],
  "timezone": "Europe/Riga",
  "privacy_notice_version": "development-fixture-v1"
}
```

Slots are actual doctor-specific options, ordered by start instant and doctor ID. Multiple eligible doctors can therefore produce the same start instant. A future UI may group these options, but must preserve the underlying doctor IDs/instants. If creation also omits `doctor_id`, the server chooses an eligible available doctor deterministically by configured sort order and ID; the receipt identifies the assigned doctor.

No available slots, an unavailable day, or a date outside the booking horizon returns `slots: []`. Invalid date/UUID syntax returns 400; an unavailable service or explicitly ineligible doctor returns 404. An unset approved privacy notice returns 503 `booking_not_configured`.

### Availability calculation

The engine resolves the verified service duration, using a doctor/service override when configured. It combines recurring intervals, inclusive effective dates, time-off ranges, occupied appointments, minimum advance notice and the booking horizon. Weekdays use Sunday = 0 through Saturday = 6. Separate working intervals model lunch breaks; the full treatment must fit within one interval, and adjacent intervals are not automatically merged.

The horizon includes today through today plus `booking_horizon_days`, measured as Riga calendar days. Advance notice uses elapsed minutes from the current instant. Slot intervals are anchored to each working interval's local start, rather than UTC midnight.

Daylight-saving behavior is deliberate: the engine enumerates actual UTC minutes projected into Riga. Nonexistent spring times never appear. Both occurrences of a repeated autumn hour remain distinct UTC starts. The frontend should distinguish repeated local labels with their offset or timezone name. As a conservative rule, treatments spanning an offset transition, including ending exactly at the transition, are excluded. This policy can be reviewed with the clinic later.

An availability response is a snapshot, not a reservation. Creation rechecks it and may return 409 if another booking has taken the slot.

## Create a guest or authenticated booking

### `POST /api/booking/appointments`

Registration is not required. Guests omit `Authorization`. Signed-in users may supply `Authorization: Bearer <Supabase-access-token>`; a valid identity is stored as the optional `auth_user_id`. An explicitly supplied empty, malformed, duplicated, expired or invalid Authorization header is rejected rather than silently downgraded to a guest. The client cannot set `auth_user_id`, actor, role, status, duration, price or end time.

```http
POST /api/booking/appointments
Content-Type: application/json
Idempotency-Key: 33333333-3333-4333-8333-333333333333
```

```json
{
  "service_id": "11111111-1111-4111-8111-111111111111",
  "doctor_id": "22222222-2222-4222-8222-222222222222",
  "first_name": "Test",
  "last_name": "Patient",
  "phone": "+371 20000000",
  "email": "patient@example.invalid",
  "starts_at": "2026-10-20T07:00:00Z",
  "privacy_acknowledged": true,
  "privacy_notice_version": "development-fixture-v1"
}
```

Validation requires names of 1–100 characters after trimming, no control characters, a plain email address up to 254 characters, and a phone containing 7–15 digits with only the permitted `+`, spaces, parentheses and hyphens. The requested start must have zero seconds and fractional seconds. Consent must be `true`, and its notice version must match the server's current version. Consent time is recorded by the server. No medical history, diagnosis, national identity number or patient profile is accepted.

New bookings return **201 Created** with a safe receipt:

```json
{
  "id": "44444444-4444-4444-8444-444444444444",
  "booking_reference": "AG-0123456789ABCDEF0123",
  "service_id": "11111111-1111-4111-8111-111111111111",
  "doctor_id": "22222222-2222-4222-8222-222222222222",
  "starts_at": "2026-10-20T07:00:00Z",
  "ends_at": "2026-10-20T07:30:00Z",
  "status": "confirmed"
}
```

Receipts omit patient names, phone, email, Auth IDs, idempotency keys and fingerprints. The owner-confirmed default `automatic` mode creates `confirmed`; a valid successful automatic receipt must not be described as waiting for administrator approval. If an administrator later chooses `manual`, creation returns `pending`. **Both reserve the slot immediately.** Pending bookings currently have no automatic expiry. Expiry, reminders and cancellation deadlines require clinic decisions; they must not be inferred by the future UI. Render the returned status instead of assuming every replay is still confirmed.

### Idempotency and retries

Generate one random UUIDv4 key for each intended submission, retain it while that submission is unresolved, and reuse it for retries of the same request. Do not derive it from patient data. The server serializes concurrent same-key attempts and binds the key to a SHA-256 fingerprint of normalized input, the optional authenticated user and the recorded actor.

An identical replay returns **200 OK** with `Idempotency-Replayed: true`, and the existing booking's current safe receipt. It does not create another appointment or event. A key reused with changed input or a different authentication/actor binding returns **409 `idempotency_conflict`**. Because the current receipt is returned, an earlier booking subsequently rescheduled/cancelled by an administrator can have an updated time/status on replay. Keys do not grant lookup access and have no current automatic expiry.

Two different keys attempting the same occupied slot produce one successful reservation and a safe **409 `slot_unavailable`** for the loser. On a transport failure or generic server failure, retry the same request/key and authentication identity before offering a fresh submission. After a definitive slot conflict, refresh availability and explicitly select a new slot before submitting a new booking intent. An `idempotency_conflict` is different: do not blindly rotate keys, because an earlier request may already have created a booking under its original authentication context.

## Optional account creation — Phase 2 contract

This is an integration contract for the future booking frontend, not an implemented signup/booking UI. The sequence is service, doctor or any doctor, date, available time, contact details, optional account choice, review and submit. Guests must remain able to book without registration.

The **Create an account** checkbox must start unchecked and be separate from the required privacy acknowledgement. Selecting it reveals password and confirm-password fields. Reuse the existing Supabase Auth signup, password validation and localized error handling; password mismatch prevents signup. An already authenticated visitor sees no account-creation checkbox, and their booking request uses their existing access token. Do not require marketing consent or treat account creation as permission for unrelated processing.

Passwords belong only in the existing Supabase registration call. They must not be sent to booking endpoints, placed in audit/idempotency data, generated without the patient knowing them, or emailed. Public registration receives role `user` through the existing database trigger, which ignores client role metadata. Neither the booking UI nor public signup may submit an authoritative admin role or use privileged Supabase credentials.

**Supabase account creation and the Go/PostgreSQL booking transaction are separate operations.** There is no distributed transaction, automatic account rollback or guarantee of joint success. Complete the requested registration step before starting the appointment request, and then apply this failure/retry contract:

| Result / failure | Required Phase 2 behavior |
| --- | --- |
| Registration is not selected | Submit a guest booking with no Authorization header after privacy acknowledgement. |
| Password mismatch or registration validation/provider failure | Show the existing localized auth error. Do not automatically submit a booking. The visitor can correct/retry registration or explicitly choose guest booking before any appointment submission. |
| Signup returns an account but no session, including email-confirmation-required configuration | Do not forge a session, silently submit as a guest, or claim a confirmed booking. Explain that account access is incomplete and require an explicit choice to continue booking as a guest. Do not re-register automatically or bypass hosted confirmation rules. |
| Signup or existing login yields a verified session | Submit the booking with that session's Bearer token. The Go API determines the user ID and role; no client `auth_user_id` is accepted. |
| Account exists, but appointment validation/availability definitively fails | Keep the account/session. Explain that the appointment was not confirmed. Let the visitor correct the booking or select another actual slot; do not delete the account automatically. |
| Booking request times out, loses its response or has an ambiguous server result | Keep the same idempotency key, exact booking payload and authentication identity. Retry that unresolved intent; do not claim confirmation or automatically issue a new key. |
| Access token expires while resolving a request | Refresh through the existing Supabase Auth client and retry using the same user ID, key and payload. A refreshed token for the same user does not change the idempotency fingerprint. If refresh fails, do not silently downgrade the attempt to a guest. |
| Visitor logs out, signs into another account, or switches from guest to account while an earlier booking outcome is unknown | Resolve the original request using its original authentication context first. The same key under a changed identity conflicts if an appointment already exists. Do not work around this by automatically using a new key; regain the original context or obtain clinic assistance. |
| API returns 201 or an idempotent 200 receipt | Display its actual status and booking reference. `confirmed` means confirmed; `pending` is possible only if manual mode was selected. A successful account signup alone never means the appointment is confirmed. |

An earlier guest booking is not automatically attached to a later account by matching email. Any future guest-to-account claim flow needs a separate secure authorization design. The backend already provides guest submission, verified-user association and request binding; UI checkbox defaults, password-mismatch behavior within booking and live signup/booking orchestration must be implemented and tested in Phase 2.

## Administrator API

Every route under `/api/admin/booking` requires a valid Supabase Bearer access token and `admin` from the server-side `user_roles` table. Missing/invalid credentials return 401, an authenticated non-admin returns 403, and unavailable Auth/role verification fails closed with 503. JWT user metadata, client state and submitted role values confer no privileges.

| Method and path | Contract |
| --- | --- |
| `GET /api/admin/booking/appointments` | Optional `date` (Riga `YYYY-MM-DD`), `doctor_id`, `service_id`, `status`, `limit`, `offset`. Limit defaults to 50, maximum 200; offset must be nonnegative. Returns `{"appointments": [...]}`, ordered by start and ID. |
| `GET /api/admin/booking/appointments/:id` | Returns one appointment, including necessary contact/consent information. Does not expose its idempotency key or fingerprint. |
| `POST /api/admin/booking/appointments` | Same body, consent, scheduling and UUIDv4 idempotency requirements as public creation. Records the verified admin as actor; does not bind the patient to the admin's Auth user. Returns 201 or replay 200. |
| `PATCH /api/admin/booking/appointments/:id/status` | Body `{"status":"confirmed"}` or another permitted target. Returns a receipt. |
| `POST /api/admin/booking/appointments/:id/reschedule` | Body `{"doctor_id":"<uuid>","starts_at":"<RFC3339-instant>","service_id":"<optional-new-service-uuid>"}`. Explicit doctor and start required. Omit `service_id` to keep the existing service. Recalculates duration for the selected service/doctor and rechecks eligibility, schedules and availability while excluding the appointment's old interval. Returns a receipt. |
| `GET /api/admin/booking/settings` | Returns the configurable booking settings and `updated_at`. |
| `PUT /api/admin/booking/settings` | Full settings update; records the verified admin and previous/new values atomically, then returns 204. Unchanged settings are a no-op. No public settings modification endpoint exists. |

Manual admin booking obeys the same confirmation mode and availability rules; with the default automatic mode it creates a confirmed appointment. It does not bypass consent or allow silent double booking. Rescheduling, doctor reassignment and service changes are restricted to pending/confirmed appointments, retain their status, and commit transactionally with collision protection. The `rescheduled` event records previous/new service IDs, doctor IDs and time ranges. Invalid eligibility or an overlapping longer replacement service leaves the original appointment unchanged. Existing appointments are not automatically rewritten when catalog durations or schedules change.

The validated lifecycle is:

| Current status | Allowed next statuses |
| --- | --- |
| `pending` | `confirmed`, `cancelled`, `rejected` |
| `confirmed` | `completed`, `cancelled`, `no_show` |
| `completed`, `cancelled`, `rejected`, `no_show` | None |

Repeating the current status is a no-op. Completion requires the appointment end to have passed; no-show requires its start to have passed. Invalid transitions return 409. Pending/confirmed/completed/no-show records occupy their historical range; cancelled/rejected records release it. Terminal appointments cannot be rescheduled.

Settings example: confirmation mode is owner-confirmed; the timing values remain technical defaults awaiting clinic approval.

```json
{
  "confirmation_mode": "automatic",
  "booking_horizon_days": 60,
  "minimum_advance_minutes": 120,
  "slot_interval_minutes": 15,
  "cancellation_policy": {},
  "timezone": "Europe/Riga",
  "privacy_notice_version": null
}
```

Bounds: horizon 1–730 days, advance notice 0–525600 minutes, interval 1–120 minutes, timezone exactly `Europe/Riga`, non-null notice version 1–100 characters. Setting its version to null disables new availability/creation until a notice is configured. `cancellation_policy` accepts a JSON object up to 4096 bytes as a future extension point; no cancellation-policy rules or guest cancellation behavior are implemented from it yet.

Migration `003_automatic_confirmation` changes the database default and existing singleton confirmation mode to automatic once, without altering existing appointments. It records the configuration change with source `migration` when values actually change. Subsequent admin changes use `booking_settings_events` with source `admin`, the verified actor, timestamp and previous/new configuration snapshots. The audit and setting change share one transaction; an audit failure rolls back the update. Later migration runs do not reset a chosen admin mode. Rollback 003 refuses to remove administrator settings history, including entries whose Auth actor has since been deleted.

## Internal configuration capabilities

`Store.SaveDoctor`, `SaveService`, `SetDoctorService`, `AddSchedule`, `RemoveSchedule`, `AddTimeOff` and `RemoveTimeOff` prepare future authenticated admin management. **They have no HTTP management routes or UI yet.** Future callers must first verify the JWT and authoritative admin role; a valid actor UUID by itself is not authorization.

Catalog methods support localized verified content, active/booking flags, sorting and provenance. Services without a duration are kept booking-disabled. Durations/overrides are positive minutes, maximum 1440. Removing doctors/services is intentionally avoided; deactivate historical records. Relationships referenced by appointments remain intact.

Schedules support multiple intervals per weekday and inclusive effective dates. An interval's end can be minute 1440. Split overnight work at local midnight. Full-day time-off boundaries must be real local Riga midnights; therefore such ranges can span 23 or 25 elapsed hours around DST. Adding time off that overlaps a pending/confirmed booking is rejected; an administrator must first resolve the booking. Removing a schedule affects future availability without deleting or cancelling existing appointments.

## Transactions, permissions and notifications

Every create transaction first serializes the idempotency key, then takes the shared booking-configuration advisory lock, then doctor locks in stable order while rechecking availability. Settings, lifecycle/reschedule and internal configuration methods take the configuration lock exclusively via `WithConfigurationLock`. Future configuration writers must use that same protocol; arbitrary SQL writers that bypass it can invalidate scheduling checks.

The PostgreSQL GiST exclusion constraint remains the final protection against overlapping `[starts_at, ends_at)` intervals for the same doctor, including inserts outside the API. Back-to-back appointments are permitted. Positive finite duration, eligibility relationships and status transitions also have database constraints. Patient creation, lifecycle events and notification-outbox inserts commit or roll back together.

All ten booking tables, including the settings audit history, enable RLS and revoke browser-role access. The inspected Go connection uses a privileged PostgreSQL identity that bypasses RLS, so API validation and authorization are the trust boundary; do not claim RLS protects this connection. Browsers call Go endpoints rather than Supabase table APIs. A future least-privilege database deployment needs reviewed grants/policies appropriate to its role. Never put database credentials or privileged Supabase keys in Vite.

Outbox rows are only queued as `pending`: creation queues booking-received and administrator notifications; automatic/manual confirmation, cancellation/rejection and rescheduling queue their relevant lifecycle notifications. No sender runs, no fake delivery is reported and no appointment reminders are scheduled. A future delivery worker must implement claiming/retries/delivery confirmation, and re-read authorized contact information using stored appointment identifiers. Audit/outbox metadata does not duplicate patient contact fields or credentials.

## Operational limits and errors

Public creation has a token bucket per network client IP: burst 5, refilling at 5 requests/minute. The in-memory map is capped at 10,000 entries; stale entries are removed on capacity pressure, and new clients fail closed if it remains full. A rejected request returns 429 `rate_limited` with `Retry-After: 60`. Failed validation and idempotent retries also consume this limit.

The limiter is single-process and resets on restart. Multi-instance production deployments need a shared/perimeter limiter and appropriate spam controls. No reverse proxies are trusted by default: forwarded client IP headers cannot bypass the limiter, but an unconfigured reverse proxy will cause clients behind it to share an IP bucket. Review exact trusted proxy/network boundaries before production rather than trusting arbitrary forwarded headers. Use HTTPS and explicit allowed CORS origins; CORS is not a substitute for authorization.

Requests receive a 12-second context deadline propagated to database/Auth operations. Health pings use a 2-second deadline; Supabase verification has its own bounded client timeout. Server read-header/read/write/idle limits also apply. GORM SQL value logging and panic request dumps are disabled, and no public response includes raw SQL/provider errors.

| HTTP status | Error code / meaning |
| --- | --- |
| 400 | `invalid_request`: malformed/unknown input, invalid IDs/date/contact/consent/settings |
| 401 | Invalid or missing required authentication |
| 403 | Authenticated identity lacks the required admin role |
| 404 | `not_found`: requested bookable entity/appointment not found or doctor ineligible |
| 409 | `slot_unavailable`, `idempotency_conflict`, or `invalid_status_transition` |
| 415 | `json_required` |
| 429 | `rate_limited` |
| 503 | `booking_not_configured`, unavailable authentication/role verification, or unhealthy database on `/api/health` |
| 500 | `booking_unavailable`: other internal/database failures; no internal details exposed |

Error JSON is `{"error":"<code>"}` for booking handlers. `/api/health` remains public and reports database connectivity; `/api/auth/me` remains authenticated, and `/api/admin/health` checks verified admin access. Neither successful health checks nor empty catalog responses imply that clinic policies/content are approved or that booking migrations were applied to Supabase.
